# ACT-R Harness：项目概览与路线图

状态日期：2026-07-22

本文档是当前实现状态和近期 demo 计划的工作基准。顶层 `README.md` 描述了更宏观的研究方向，但今天参与代码工作的协作者应以本文档为准，了解项目下一步要跑什么、差距在哪里。

---

## 当前目标

当前阶段的目标是让整个 harness 使用 `shared/ruleset/lab.yml` 中的活跃程序性规则端到端跑通。

本阶段的可交付物是一个最小化的代码库导航 demo，满足以下条件：

- Python 提供声明性记忆、程序性记忆和神经核心的 gRPC 服务。
- C# host 持有运行时 buffer / 模块，执行解码后的操作，并驱动步骤循环。
- Host 从一个已种下的 goal 出发运行，直到完成或耗尽，写出有用的日志和简单报告。

本阶段的"完整 harness"定义为：`shared/ruleset/lab.yml` 中的活跃规则能正确运行。文件中注释掉的未来规则不在第一次 demo 的要求范围内。

---

## 项目是什么

从高层看，ACT-R Harness 是一个横跨共享 protobuf 合约、Python 服务和 C# host 的神经符号运行时：

- `shared/proto`：两个运行时共用的 gRPC 合约。
- `shared/ruleset/lab.yml`：代码库导航场景的当前程序性规则集。
- `python/src/actr_harness`：声明性记忆、程序性记忆和神经核心的 gRPC 服务。
- `python/tests`：对 `lab.yml` 中的条件评估和动作解码进行测试的测试套件。
- `Dotnet/src/Harness.Core`：步骤循环、模块注册表、gRPC 客户端和核心模块。
- `Dotnet/src/Harness.Codebase`：文件探索和代码视口等代码导航模块。
- `Dotnet/src/Harness.Host`：将所有服务连接起来并运行 epoch / step 的可执行 host。

预期的运行时分工如下：

1. C# host 从各模块收集 buffer 状态。
2. Host 向 Python 程序性记忆请求所有规则的条件。
3. Host 向 Python 神经核心询问哪些规则的条件被满足。
4. Host 向 Python 程序性记忆请求选出一条规则。
5. Host 向 Python 神经核心请求将该规则的动作解码为具体的 `BufferOperation`。
6. C# host 将这些操作应用到本地模块。
7. Host 记录步骤追踪，继续运行直到终止。

## `lab.yml` 中的活跃规则

当前 demo 规则定义了一个小型代码库导航循环：

- **`rule-init`**：若 `intention.current_goal.slots.status == "start"`，则查询声明性记忆，将 goal 状态推进到 `memory_queried`。
- **`rule-memory-hit`**：若状态为 `memory_queried` 且检索到了 chunk，则派生注意力标签，可选地从记忆中打开文件，将 goal 状态推进到 `file_opened`。
- **`rule-memory-miss`**：若状态为 `memory_queried` 且没有检索到 chunk，则推送一个 `ExploreFileSystem` 子目标。

后续的文件探索和视口规则目前仅以注释草稿的形式存在，属于下一阶段，不在第一次最小 demo 的范围内。

## 阻塞 Demo 的具体缺口

当前代码中可以看到以下主要阻塞点：

| 位置 | 问题描述 |
|------|----------|
| `python/src/actr_harness/services/procedural_memory.py` | `self.rules` 已初始化但从未填充；服务目前不加载 `shared/ruleset/lab.yml`，`GetAllConditions` 会返回空。 |
| `Dotnet/src/Harness.Core/Extensions/DependencyInjectionExtensions.cs` | 只注册了 `DeclarativeMemoryModule` 和 `IntentionModule`；活跃规则还需要 `FileExplorerModule` 和 `CodeViewportModule`。 |
| `Dotnet/src/Harness.Abstractions/IEmbeddingService.cs` | `FileExplorerModule` 依赖 embedding 服务，但目前没有任何实现。 |
| `Dotnet/src/Harness.Core/HarnessCore.cs` | `StepAsync()` 无条件返回 `true`，导致 runner 在一步后立即停止。 |
| `Dotnet/src/Harness.Host/HarnessRunner.cs` | 循环期望 `StepAsync()` 发出终止信号，但当前行为使每个 epoch 立即结束。 |
| `Dotnet/src/Harness.Host/Program.cs` 和 `GrpcClientsOptions.cs` | Host 配置中仍然包含 `FrostpunkWorldAddress`，该地址不在当前 demo 路径中。 |
| 无任何组件 | 启动时没有种下初始 intention goal（如 `{ id, query, status = "start" }`），`rule-init` 没有可以匹配的内容。 |
| 无日志 / 报告管道 | 没有可供其他开发者无需调试器即可检查的步骤追踪。 |

## 最小 Demo 范围

第一次 demo 应刻意保持小规模：

- 只使用 `shared/ruleset/lab.yml` 中的三条活跃规则。
- 启动时在 intention 模块中种下一个根 goal。
- 演示两条路径：
  - memory-hit（记忆命中）
  - memory-miss（记忆未命中）
- 记录每个步骤，并将简单报告保存到磁盘。
- 尽可能保持确定性或接近确定性的行为。

第一次 demo 推荐的非目标：

- 暂不实现注释掉的后续规则。
- 暂不优化 utility 学习。
- 不将 Frostpunk / household 环境相关组件纳入关键路径。
- 不要求外部 UI。

## 推荐工作流

以下任务可以由不同协作者并行推进。

### 1. Python 服务补齐

**目标**：让程序性记忆真正能够服务当前规则集。

预期产出：

- 启动时加载 `shared/ruleset/lab.yml`。
- 将 YAML 规则转换为 `ProceduralCondition` 和 `NeuroAction` 对象。
- 为每条规则设置稳定的初始 utility 值。
- 添加一个小型单元测试，验证服务能正确加载三条活跃规则。

### 2. C# Host 模块注册

**目标**：注册活跃规则所需的模块。

预期产出：

- 在 host / core 路径中引用 `Harness.Codebase`。
- 注册 `FileExplorerModule` 和 `CodeViewportModule`。
- 添加一个简单的 `IEmbeddingService` 实现用于 demo。

推荐方式：

- 对于最小 demo，本地确定性 fallback 足够用，可以基于 token overlap，甚至返回简单固定向量，只要 `FileExplorerModule` 能在不依赖外部服务的情况下运行即可。

### 3. 步骤循环与终止逻辑

**目标**：让 host 能运行超过一步，并因正确的原因停止。

预期产出：

- 修改 `HarnessCore.StepAsync()`，使其返回有意义的终止信息。
- 将"没有满足条件的规则"作为正常结束状态处理，而非未处理的失败。
- 在第一步之前种下初始 goal。
- 为第一次 demo 定义明确的停止条件，例如：
  - 没有可用规则
  - 达到最大步数
  - 活跃 goal 达到终态状态

### 4. 日志与报告

**目标**：让每次运行对其他开发者可检查。

预期产出：

- 每步的结构化日志，包含：
  - 步骤编号
  - 满足条件的规则 ID 列表
  - 选中的规则 ID
  - 解码后的操作
  - 步骤前后的 buffer 状态
  - 错误信息和停止原因
- 保存的报告产物，例如：
  - `artifacts/runs/<timestamp>/trace.jsonl`
  - `artifacts/runs/<timestamp>/summary.md`

对于第一次 demo，纯 JSONL 加一份简短的 Markdown 摘要已经足够。

### 5. Demo 打包

**目标**：让刚加入项目的人能轻松运行 demo。

预期产出：

- 一份真实的 `appsettings.json` 示例文件。
- Python 和 C# 的精确启动命令。
- 一个有文档记录的样本场景，包括初始 goal 和预期结果。

## 最小 Demo 的完成标准

当以下所有条件均满足时，本阶段完成：

- [ ] Python 程序性记忆能从 `shared/ruleset/lab.yml` 加载活跃规则。
- [ ] C# host 携带已种下的 goal 启动，能执行多步。
- [ ] Host 拥有活跃规则所需的全部模块：
  - `declarative_memory`
  - `intention`
  - `file_explorer`
  - `code_viewport`
- [ ] 至少一次运行演示了 memory-hit 路径。
- [ ] 至少一次运行演示了 memory-miss 路径。
- [ ] 每次运行产出可读日志和保存的报告。
- [ ] 新协作者能按照安装说明复现 demo，无需先阅读代码。

## 建议执行顺序

如果由一人按顺序完成所有工作，以下顺序是最短路径：

1. 将规则加载进 Python 程序性记忆。
2. 注册缺失的 C# 模块，添加最简 embedding 服务。
3. 种下初始 goal，修复循环终止逻辑。
4. 添加日志 / 报告输出。
5. 添加一个端到端冒烟测试或可复现的手动 demo 脚本。

第一次 demo 稳定后，下一步有价值的扩展是：

1. 实现 `lab.yml` 中注释掉的文件探索和定位特定行的规则。

4. 将顶层 README 与实际可运行的场景对齐，使架构说明、demo 范围和研究路线图清晰分离。
